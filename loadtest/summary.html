二、压测曲线

写路径在 100 并发达到拐点（399 TPS / P99 273ms）；继续加压到 200 并发，TPS 反降至 350，P99 涨到 1024ms —— 典型的线程池/连接池排队。

四、一致性校验（并发下是否超发）

  • 压测前把测试券库存重置为 100000，Redis 计数清零。
  • 三轮写压测共 8000 次成功；结束后 Redis totalNum = 92000，扣减量与成功数完全一致。
  • 落库侧 user_coupon 行数 = 15145，与历次成功请求数逐条对齐（MQ 异步落库，压测后约 8s 追平）。
  • 结论：Lua 原子扣减 + 分布式锁下未出现超发、未出现“扣了库存没落库”的漂移。

五、测试方法

  • 账号：批量创建 1120 个学生账号（BCrypt 口令），每轮压测前重新登录换取 JWT；token 有效期仅 5 分钟，故「登录 → 压测」串行执行。
  • 避免 CSV 锁：JMeter 的 CSV Data Set 在 shareMode.all 下每次取样都要抢文件锁，实测把吞吐压到 ~100 TPS；改为 每线程独立 token 文件（${__threadNum}.csv）后吞吐才反映真实服务端能力。
  • 数据隔离：使用专属测试券 1900000000000000001（库存与限领均为 10 万），不触碰业务券；压测产生的 15145 行数据已清理。
  • 断言：响应体包含 "code":200，非 200 计为失败。

六、口径与局限

  • 压测机与被测 VM 共用一台物理机（VMware NAT），200 并发时压测机自身也可能是瓶颈，故 200 并发数值偏保守。
  • 未接入 JVM/GC/CPU 监控，瓶颈定位仅到「接口 + 中间件」层面；如需进一步定位，建议在 VM 内用 top -Hp + jstack 看线程池排队。
  • 读接口的 540ms P99 与其数据量相关：每用户 1 条记录时测得；当单用户累积到上百条时（压测中途曾出现），P99 升至 1509ms，EXPLAIN 显示 Using filesort（索引为 user_id,coupon_id，未覆盖 create_time 排序）——这是可以落地的优化点。
